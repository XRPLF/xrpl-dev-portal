# Batchトランザクション

Batchトランザクションでは、複数の[トランザクション](index.md)をまとめてパッケージ化し、単一のユニットとして実行できます。部分的な完了や予期しない結果のリスクを排除し、複雑な操作をより信頼性が高く予測可能な方法で実行できます。1つのバッチで最大8件のトランザクションを送信できます。

{% amendment-disclaimer name="BatchV1_1" /%}

## バッチの使用例

`Batch`トランザクションの使用例として、以下が挙げられます。
- 全て成功か全て失敗：NFTをミントして同時にオファーを作成できます。オファー作成が失敗した場合、NFTミントも取り消されます。
- 複数のオファーの試行：異なるスリッページ量で複数のオファーを送信しますが、成功するのは1つだけです。
- プラットフォーム手数料：プラットフォーム手数料をトランザクション自体に含めることで、プロセスを簡素化できます。
- スワップ（マルチアカウント）：複数のアカウント間でのトラストレスなトークン/NFTスワップ。
- アカウント引き出し（マルチアカウント）：当座預金からの引き出しを試行し、失敗した場合は代わりに普通預金から引き出します。

`Batch`トランザクションは、ラッパーである`Batch`トランザクション自体の _外部トランザクション_ と、それぞれがアトミックに実行される _内部トランザクション_ で構成されます。内部トランザクションの正確な処理方法は、バッチ _モード_ によって決まります。

## バッチのモード

`Batch`には`ALLORNOTHING`、`ONLYONE`、`UNTILFAILURE`、`INDEPENDENT`の4つのモードがあります。

### All or Nothing（全て成功か全て失敗）

`ALLORNOTHING`モードでは、いずれかの内部トランザクションが成功するには、全ての内部トランザクションが成功する必要があります。

### Only One（1つだけ）

`ONLYONE`モードでは、最初に成功したトランザクションのみが成功します。他の全てのトランザクションは失敗するか、実行されません。

### Until Failure（失敗まで）

`UNTILFAILURE`では、全ての内部トランザクションをいずれかが失敗するまで適用します。最初の失敗後の全てのトランザクションは適用されません。

### Independent（独立）

1つ以上の内部トランザクションが失敗しても、全てのトランザクションが適用されます。


## メタデータ

内部トランザクションはレジャーに個別にコミットされるため、個別のメタデータを持ちます。これにより、レガシーシステムがシステムの変更を必要とせずに`Batch`トランザクションをサポートできるよう、より良い後方互換性が保証されます。

例えば、2つの内部トランザクションを含む1つの`Batch`トランザクションのみを持つレジャーは、次のようになります。

```
[
  OuterTransaction,
  InnerTransaction1,
  InnerTransaction2
]
```

### 外部トランザクション

各外部トランザクションには、内部トランザクション処理ではなく、シーケンスと手数料処理のメタデータが含まれます。エラーコードは外部トランザクション処理（例：シーケンスと手数料）のみに基づいており、内部トランザクション処理が失敗しても`tesSUCCESS`の結果を返します。

### 内部トランザクション

各内部トランザクションには、独自の処理のメタデータが含まれます。実際にレジャーにコミットされた内部トランザクションのみが含まれます。これにより、レガシーシステムが`Batch`トランザクションを通常のトランザクションのように処理することが容易になります。

親の外部トランザクション（`ParentBatchID`）への逆ポインタもあります。


## Batchトランザクションのセキュリティ

`Batch`トランザクションには追加のセキュリティ考慮事項があります。

### 信頼の前提

`Batch`トランザクションに含まれるアカウントのトランザクション数に関係なく、全てのアカウントが一連のトランザクションに署名する必要があります。

#### 単一アカウント

単一アカウントの場合、その単一アカウントは送信する全てのトランザクションを承認する必要があります。他のアカウントは関与しません。

#### マルチアカウント

マルチアカウントの場合はより複雑で、例で最もよく説明できます。

アリスとボブがマルチアカウント`Batch`を介してトラストレススワップを行っており、アリスが1000 XRPを提供し、ボブが1000 USDを提供します。ボブが`Batch`トランザクションを送信するため、アリスはスワップにおける自身の担当分をボブに提供する必要があります。

アリスが完全に自動入力され署名されたトランザクションをボブに提供した場合、ボブは自分のトランザクションを送信せず、アリスのトランザクションのみをレジャーに送信して、1000 USDを失うことなく1000 XRPを受け取ることができます。したがって、内部トランザクションは署名されていない必要があります。

アリスが`Batch`トランザクションのうち自身の担当分のみに署名した場合、ボブは自分のトランザクションを1 USDのみを提供するように変更でき、それによってはるかに安い価格で1000 XRPを取得できます。したがって、`Batch`トランザクション全体（とその全ての内部トランザクション）は全ての当事者によって署名される必要があります。

### 内部トランザクションの安全性

バッチの内部トランザクションは特殊なケースです。署名や手数料を含みません（これらは両方とも外部トランザクションに含まれているため）。したがって、誰かが外部トランザクションに含めることなく、`Batch`の内部トランザクションを直接送信されないようにするために、慎重に処理する必要があります。

内部トランザクションはブロードキャストできません（例えば悪意のあるノードからブロードキャストされた場合、受け入れられません）。代わりに`Batch`の外部トランザクションから生成される必要があります。内部トランザクションは、submit RPCを介して直接送信することはできません。

## 制限事項

`Batch`トランザクションは[simulateメソッド][]と互換性がありません。`simulate`は単一のトランザクションのみを対象としたドライランとして動作するため、内部トランザクションをコンセンサスセットに追加する効果をシミュレートすることはできません。

## 統合時の考慮事項

`Batch`トランザクションには、統合時に固有の考慮事項があります。

- 内部トランザクションが失敗した場合でも外部トランザクションは`tesSUCCESS`を返すため（[メタデータ](#メタデータ)をご覧ください）、各内部トランザクションのメタデータと結果コードを確認して、実際の結果を判断する必要があります。
- 内部トランザクションが検証された場合、それらは外部トランザクションと同じレジャーに含まれます。内部トランザクションが異なるレジャーに現れた場合、それは不正の試みである可能性が高いです。
- `Batch`トランザクションを特別に処理しないシステムでも、各内部トランザクションはそれ自体で有効なトランザクションであるため、変更なしでサポートできるはずです。`tes`（成功）または`tec`の結果コードを持つ全ての内部トランザクションは、[`tx`](../../references/http-websocket-apis/public-api-methods/transaction-methods/tx.md)や[`account_tx`](../../references/http-websocket-apis/public-api-methods/account-methods/account_tx.md)などの標準的なトランザクション取得の仕組みを通じてアクセスできます。
- マルチアカウントの`Batch`トランザクションでは、バッチの署名者は、外部トランザクションのアカウント、シーケンス、バッチモードのフラグ、および各内部トランザクションのハッシュに署名します。これらのいずれかを後から変更すると、署名は無効になります。手数料は外部トランザクションの中で唯一署名 _されない_ 部分であるため、送信者は他の当事者と調整することなく手数料を設定できます。

以下のセクションでは、特定の種類の統合に関する追加の推奨事項を説明します。

### クライアントライブラリ

`Batch`トランザクションのサポートを実装するクライアントライブラリは、以下を行うべきです。

- `Batch`トランザクションの手数料には全ての内部トランザクションの手数料の合計が含まれるため、手数料を計算するヘルパーメソッドを提供する。[特殊なトランザクションコスト](../../references/protocol/transactions/types/batch.md#特殊なトランザクションコスト)をご覧ください。
- 一方の当事者が外部トランザクションに署名し、他の当事者が内部トランザクションに署名する、マルチアカウントの`Batch`トランザクションを構築・署名するヘルパーメソッドを提供する。
- 各内部トランザクションの`Fee`を`"0"`に、`SigningPubKey`を空文字列（`""`）に設定し、`TxnSignature`フィールドを省略する自動入力メソッドを提供する。

### ウォレット

`Batch`トランザクションを表示または署名するウォレットは、以下を行うべきです。

- 署名を要求する前に全ての内部トランザクションをユーザーに明確に表示し、ユーザーが承認する内容の全体像を理解できるようにする。
- マルチアカウントの`Batch`トランザクションについては、ユーザーがバッチ内の自身の担当分を確認して署名し、他の当事者が署名できるようにエクスポートするワークフローを提供する。
- 他のアカウントの内部トランザクションを含む`Batch`トランザクションに署名する場合、バッチ全体を承認することになるため、ユーザーに警告する。
- [バッチモード](#バッチのモード)を表示し、その意味を説明する。
- 検証されるトランザクションの数はバッチモードとどの内部トランザクションが成功したかに依存するため、成功または失敗の後にシーケンス番号を自動的にインクリメントしないようにする。代わりに、外部の`Batch`トランザクションが検証されるのを待ち、各内部トランザクションの結果を確認して、どのシーケンスが消費されたかを判断する。

### エクスプローラーとインデクサー

`Batch`トランザクションを表示するエクスプローラーとインデクサーは、以下を行うべきです。

- 内部トランザクションのメタデータにある`ParentBatchID`フィールドを使用して、外部の`Batch`トランザクションとその内部トランザクションの関係を表示する。
- 内部トランザクションを独立したトランザクションとしてではなく、外部の`Batch`トランザクションとの関連の中で表示する。
- わかりやすさのため、トランザクション一覧では内部トランザクションを外部トランザクションとグループ化することを検討する。

## セキュリティ監査

`Batch`トランザクションはHalbornによる独立した監査（2025年1月〜2月）を受け、アトミック性の処理における重大な欠陥が特定され、リリース前に修正されました。詳細は[監査レポート](https://www.halborn.com/audits/ripple/ripple---batch---smart-contract-assessment-420598)をご覧ください。

2026年2月には署名検証に関する別の脆弱性が発見され（[脆弱性開示レポート](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026)をご覧ください）、`BatchV1_1` Amendmentで修正されました。Halbornは2026年3月〜4月にこの修正を再監査しました。詳細は[再監査レポート](https://www.halborn.com/audits/ripple/batch-re-audit-314089)をご覧ください。
